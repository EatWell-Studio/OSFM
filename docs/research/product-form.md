# 产品形态调研

> 调研日期：2026-11-25。输入：项目发起讨论的总结（内部文档）、本目录下的其他调研。本文回答"OSFM 是什么样的产品、给谁用、第一版做什么"，技术选型见 [tech-stack.md](tech-stack.md)，合规见 [geodata-and-compliance.md](geodata-and-compliance.md)。

## 1. 一句话定位

**一个熟人圈自己的美食地图：地图是展示层，圈内成员署名的推荐是数据层。**

它不是又一个地图工具，也不是点评平台。和大众点评、Google Maps 的区别不在于"地图画得好不好"，而在于**谁说的**：每个点都能追溯到一个你认识的人。

| 维度 | 点评 / 地图平台 | OSFM |
| --- | --- | --- |
| 数据来源 | 陌生人众包，平台排序 | 圈内成员，按人署名 |
| 信任来源 | 评分 + 平台反作弊 | 熟人关系：污染成本 = 成为群友 |
| 范围单位 | 城市 / 全国 | 一个圈子（一个群） |
| 数据归属 | 平台 | 圈子自己的实例，可完整导出 |
| 商业动机 | 广告、团购、商家推广 | 无；不接受商家任何形式的付费 |
| 覆盖面 | 尽量全 | 只要"我们的人去过、愿意推荐的" |

## 2. 用户与场景

### 2.1 用户单位

用户单位是**一个熟人圈**，典型规模几十到几百人：成员互相在群里聊过天，知道彼此的口味与可信程度；地理上分散（国内多城 + 海外），旅行时会经过彼此推荐过的地方。

圈内的角色：

| 角色 | 需要什么 |
| --- | --- |
| 旅行者（最常见） | 到了一个城市，打开就看到"群友说这几家好"，附近、现在开着、适合当前时段的 |
| 推荐人 | 用最少的步骤把一家店记下来，并且能控制"以什么名义、给谁看" |
| 实例维护者（1–2 人） | 一台家用设备或小服务器就能跑；升级、备份不费心；邀请与移出成员 |
| 潜在新成员 | 通过邀请进入，进门就能看到已有内容 |

### 2.2 核心场景

1. **出行前 / 到达时浏览**：打开城市 → 地图上看到推荐点 → 按时段（早餐 / 夜宵）、类别筛选 → 看推荐语和推荐人 → 一键跳转导航。
2. **随手记一家店**：在店里或回来后，打点（或从分享链接导入）→ 写一句推荐 → 选时段、署名方式、可见性 → 保存。目标是 30 秒内完成。
3. **群聊里说过的推荐沉淀下来**：把群里的"这家羊杂汤在小酥肉对面"变成地图上的点，并保留原话、原链接作为来源。
4. **现场问群友**（人工兜底）：地图上没有、或不确定还开不开时，从地图一键分享位置到群里问。这条讨论里明确要保留，参与感本身是产品的一部分。
5. **圈子间分享**（远期）：订阅另一个圈子的实例，看到对方愿意公开给你的推荐。

### 2.3 现状（真正的竞争对手）

今天这些推荐的去处：群聊记录（搜不到、没坐标）、个人在各地图 App 里的收藏（只有自己能看）、小红书笔记（混有软广）。OSFM 首先要比"在群里发一句话 + 以后翻聊天记录"更省事，否则没人会用。由此得出两条设计约束：

- **录入成本必须极低**：允许只填店名 + 一个大致的点 + 一句话；其他字段全部可选。
- **入口要贴近群聊**：分享链接、二维码、"复制为群消息"的文本格式。

## 3. 信任模型

这是 OSFM 与其他产品的根本区别，也是最需要先设计清楚的部分。

### 3.1 进入：邀请制

- 不设公开注册。新成员只能通过现有成员的邀请链接 / 邀请码进入。
- **记录邀请树**（谁邀请了谁，参照 Lobsters 的做法）：出了问题能顺着邀请关系追溯，维护者可以整枝撤销。
- 邀请码一次性、可设有效期；维护者可以关闭某个成员的邀请权限。

### 3.2 署名：每条推荐都有推荐人

- 每条推荐绑定一个成员身份，不存在匿名提交。
- 讨论中提到的"附推特 ID 导入现成信誉链"：作为**可选的外部身份链接**展示在成员资料上，而不是登录方式（见 [tech-stack.md](tech-stack.md) 的身份部分，X API 成本与国内可用性都有问题）。

### 3.3 隐私：化名与逐条可见性

讨论里明确的需求是：成员需要在"实名"与"不让熟人圈外的人认出我"之间切换。设计成两层：

| 层 | 选项 | 说明 |
| --- | --- | --- |
| 显示身份（每条推荐选择） | 主名 / 化名 | 化名在实例内稳定（同一个化名的推荐能聚合在一起），但不对外暴露与主名的关联；维护者在必要时可见，用于处理滥用 |
| 可见范围（每条推荐选择） | 仅自己 / 圈内 / 允许联邦（远期） | 默认"圈内"；"允许联邦"在联邦实现之前只是一个预留值 |

需要注意的风险：化名 + 外部账号链接 + 时间地点，组合起来可能把人认出来（去匿名化）。所以化名推荐**不显示外部账号链接**，导出时化名与主名的映射不进入公共导出。

### 3.4 交互参照：社区可标记地图

讨论中提到的交互参照"明日方舟蟑螂地图"即 2026-11 走红的同人站 舟P地图 / 舟友地图（见 [open-source-landscape.md](open-source-landscape.md) §6）：玩家在地图上放一个代表自己的标记，联系方式要双方同意才互相可见，受信任用户的举报累计到一定数量就先隐藏、再人工复核。可借鉴的是"放一个点"的低门槛、双向同意的信息公开，以及"先隐藏后复核"的处理方式；与 OSFM 的区别是那里标记的是人，这里标记的是店，因此 OSFM 不展示任何成员的位置。

### 3.5 退出与清理

- 成员可以删除自己的全部推荐，或选择"离开但保留推荐（转为化名 / 匿名化归档）"。
- 维护者移出成员时，可选择保留或隐藏其推荐。

## 4. 地点与"相对坐标"

讨论里的种子数据几乎全是相对描述：「小酥肉对面」「大皮院巷子口」「莲湖公园南小区底商」。这类描述地理编码解析不了，OSM 里也常常没有对应的店铺节点。产品上的处理：

1. **人工打点是主路径**：长按地图放一个点，或拖动微调；默认以当前定位或当前地图中心为起点。
2. **保留原话**：`位置描述` 作为独立字段原样保存（"斜对面 / 巷子口"），显示在推荐上。到了现场，这句话往往比坐标更有用。
3. **锚点引用（可选）**：允许把一个地点关联到另一个地点（"在 X 对面"），关联到的是实例内的地点或 OSM 节点；这样一个精确的锚点能帮助其他相对点。
4. **精度标记**：每个点带一个精度级别（精确到门口 / 大致在这条街 / 只知道这一片），地图上用不同样式显示，避免把"大概在这附近"画得像精确坐标。
5. **补到 OSM（可选、慎重）**：给愿意的成员提供"去 OSM 补这个店铺节点"的引导（跳转 iD 编辑器 / StreetComplete / MapComplete 的对应页面），OSFM 自身不直接写 OSM。合规边界见 [geodata-and-compliance.md](geodata-and-compliance.md)。

**地点与推荐分开建模**：一个地点可以有多个成员的多条推荐（这正是熟人地图有价值的地方：三个人都推荐过的店）。

## 5. 数据模型草案（供 PRD 讨论）

```
Place（地点）                              —— 地点层：ODbL 1.0，不含任何成员信息
  id            UUID（全局稳定，联邦时用）
  name          店名（可多语言 / 别名）
  location      WGS-84 点；precision（exact | street | area）
  position_note 原话位置描述（"小酥肉对面"）
  anchor_place  可选，相对于哪个地点
  osm_ref       可选，关联的 OSM 节点 / 路（node/123）
  tags          类别、菜系：类别限定为餐饮白名单（OSM amenity=restaurant / fast_food / cafe 等），
                菜系沿用 OSM cuisine 取值；不允许自由类型（合规原因见 geodata-and-compliance.md §0）
  status        营业中 / 疑似关门 / 已关门（带最后确认时间）

Recommendation（推荐）                     —— 推荐层：内容许可另定（建议 CC BY-SA 4.0）
  id            UUID
  place_id
  author_id     成员；display_as（主名 | 化名 id）
  visibility    private | circle | federated（预留）
  text          推荐语（"人多可不去"、"早上人少"也属于推荐的一部分）
  dishes        推荐的菜
  time_slots    早餐 / 午 / 晚 / 夜宵；季节（"冬天"）
  sources[]     来源：url、类型（群聊转述 / 笔记 / 本人到店）、原文摘录
  visited_at    最近一次到店（可选）
  created_at / updated_at

Member（成员）                             —— 成员层：个人数据，只在实例内使用，不随数据层导出
  id, display_name, pseudonyms[], external_links[]（如 X 账号，可选）
  invited_by, role（member | maintainer）, can_invite
```

### 5.1 数据层与许可

许可按**数据层**划分，而不是按每条数据的来源划分：同一层里混在一起的数据，只能整体适用一个许可。

| 层 | 内容 | 许可 | 理由 |
| --- | --- | --- | --- |
| 地点层 | `Place` 的全部字段：坐标、店名、类别、精度、原话位置描述、`osm_ref`、营业状态 | **ODbL 1.0（整层）** | 吸附到 OSM 节点的点带有 OSM 的坐标与名称，成员自己打的点是对照 OSM 底图补充同一类要素（餐饮）；两者在同一区域混合，按 OSMF 的 [Collective Database](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Collective_Database_Guideline_Guideline) 与 [Horizontal Map Layers](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Horizontal_Map_Layers_-_Guideline) 指南属于衍生数据库，触发共享相同方式 |
| 推荐层 | `Recommendation` 的全部字段：推荐语、菜品、时段、来源、推荐人引用 | **另定，建议 CC BY-SA 4.0**（或由实例选择） | 只通过 `place_id` 引用地点、本身不含 OSM 数据；按 Collective Database 指南（"为 OSM 餐馆补充电话号码"一例）与地点层相互独立，不受 ODbL 约束 |
| 成员层 | `Member`、邀请关系、化名映射 | 不对外授权 | 个人数据，只在实例内使用 |

由此带来的设计约束：

1. **地点层不放任何成员信息。** 谁添加了地点、谁确认了营业状态，记在推荐层或单独的审计表里；否则按 ODbL 导出地点层时会带出成员身份，与化名设计冲突。
2. **ODbL 的"公开使用"包括邀请制圈子**（ODbL 1.0 §1："Publicly" 指本人以外的任何人）。义务对象是拿到数据的人，即实例成员：实例为成员提供地点层的 ODbL 导出即可满足，不需要向圈外发布。
3. **署名**：地图上与地点层导出里都保留 "© OpenStreetMap contributors"。
4. **不依赖"少于 100 个要素"的豁免**：[Substantial 指南](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Substantial_-_Guideline)把同一项目的多次小量提取合并计算，持续运行的实例很快会超过。
5. **来源里的第三方原文不随推荐层的许可**：`sources[]` 的原文摘录（笔记、帖子）仍属原作者，只保留必要的短摘录与链接，导出时标明出处。
6. 推荐层与地点层分表存放、分别导出；联邦同步时也按层传输，各自带许可声明。

关于讨论里提到的 **source-of-truth 字段**（平台展示的不一定是实际情况，以原始来源为准）：落在 `sources[]` 上，每条推荐保留它的出处与原文；当平台信息（营业时间、地址）与成员亲见不一致时，以成员到店的记录为准，并标注确认时间。

## 6. MVP 范围建议

| 必须有（第一版） | 第二步 | 远期 / 不做 |
| --- | --- | --- |
| OSM 底图上显示圈内推荐点，按时段 / 类别筛选 | 从地图 App 分享链接导入坐标（需坐标转换） | 实例间联邦订阅 |
| 打点 + 写推荐（店名、位置描述、时段、来源链接） | 成员主页：某人推荐过的所有店 | 托管服务（商业化） |
| 邀请制注册、邀请树 | "想去 / 去过"个人标记 | 区块链、代币、积分兑换（明确不做） |
| 主名 / 化名、逐条可见性 | 照片（注意存储与隐私） | 公开注册、商家认领（明确不做） |
| 一键跳转导航（高德 / Apple / Google） | 游戏化：点亮一条街解锁称号 | 评分 / 星级平均（不做，见下） |
| 导入 / 导出（GeoJSON、CSV） | 离线缓存一个城市 | |
| 把一个点"分享到群里" | 营业状态众包确认 | |

**不做星级评分**：熟人推荐的价值在"谁、为什么推荐"，平均分会把它压扁成一个数字，并重新引入刷分动机。用"推荐 / 有保留的推荐（"人多可不去"）"和推荐人数代替。

### 6.1 游戏化（可选）

"点亮整条街解锁称号"适合作为第二步的轻量机制：以街道 / 片区为单位统计"圈内推荐过的店"与"我去过的店"。要避免的是任何能被兑换或比较排名后引发刷量的设计；称号只做展示。

## 7. 产品形态选择

| 形态 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| **PWA（移动优先的网页，可安装）** | 一套代码；自部署实例天然就是一个网址；国内外都能打开；可离线缓存 | iOS 上推送与后台能力有限 | **第一版采用** |
| 原生 App | 体验最好、离线地图成熟 | 每个实例一个 App 不现实；上架成本高 | 不做 |
| 微信小程序 | 贴近群聊 | 需要国内主体、备案，地图组件只能用腾讯地图，与"自部署 + OSM"冲突 | 不做；用"分享到群"的链接与卡片文本弥补 |
| 机器人（Telegram / 群机器人） | 录入贴近聊天 | 浏览地图仍需网页；平台依赖 | 远期作为录入入口 |
| 直接用 uMap 等现成工具 | 零开发 | 没有邀请、署名、化名、可见性 | 作为 MVP 之前的过渡方案，见 [open-source-landscape.md](open-source-landscape.md) |

## 8. 部署形态

- **一个圈子一个实例**，由圈内 1–2 名成员维护。目标硬件下限：2 核 / 8 GB 的机顶盒级 ARM 设备；上限无所谓。
- **单进程 + SQLite**，一个 Docker 镜像（x86_64 与 ARM64），数据目录一个，备份就是复制这个目录。
- 家用网络部署需要解决外网访问（内网穿透 / 反向代理），以及国内外成员都能访问的问题，见 [tech-stack.md](tech-stack.md)。
- **不做中心化 SaaS**：讨论中已否决"一个中心库混合多个圈子"。是否以后提供"代为托管的独立实例"是开放问题。

## 9. 联邦（远期，但现在要留接口）

联邦是"成功之后的烦恼"，第一版不实现，但以下几点从第一天起就要做对，否则以后改不动：

1. 所有对象用全局唯一、稳定的 UUID，不用自增 ID 对外。
2. 可见性字段从第一天起包含"允许联邦"这个值。
3. 导出格式（GeoJSON + 扩展属性）有版本号，作为将来实例间同步的基础。
4. 推荐人的身份在导出里可以是"实例 + 成员 id"的形式，不泄露化名映射。

## 10. 风险与需要验证的假设

| 假设 / 风险 | 验证方式 |
| --- | --- |
| 群友愿意花 30 秒录入，而不只是在群里说一句 | 用种子数据 + 过渡方案先跑两周，看录入数 |
| 一个圈子的推荐足够密，旅行时能派上用场 | 统计推荐的城市分布；考虑联邦或圈子间分享作为解法 |
| 维护者愿意自部署并持续维护 | 一键部署、自动备份、升级无需手动迁移 |
| 化名真的能保护成员 | 威胁建模：哪些字段组合能认出人 |
| OSM 底图在国内的店铺级覆盖不够 | 这正是 OSFM 的数据层存在的原因：不依赖 OSM 有这个店 |
| 国内访问海外实例的速度 / 可达性 | 部署方案调研与实测 |

## 11. 交给 PRD 的开放问题

1. 化名的语义：一个人可以有几个化名？化名能否跨圈子使用？
2. 推荐的编辑权：只能本人改？维护者能否隐藏？
3. "到店现场问群友"做成什么：分享卡片、群机器人，还是实例内的讨论串？
4. 营业状态由谁维护、多久失效？
5. 第一个城市 / 第一批种子数据如何录入（谁打点、谁核对）？
6. 软件 license 与推荐层的内容许可（见 [open-source-landscape.md](open-source-landscape.md) 的建议与上面 §5.1；地点层随 OSM 用 ODbL 已无选择余地）。
