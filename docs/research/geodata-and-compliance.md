## 0. 风险汇总表

| 风险项 | 适用场景 | 等级 | 产品对策 |
|---|---|---|---|
| 在中国境内**公开**提供带"上传标注"的互联网地图服务，却没有测绘资质和审图号（《地图管理条例》第33、38、54条；《测绘法》第38、55、62条） | (b) 在中国大陆公开托管 | **高** | 不支持、不建议在大陆做公开实例。文档里写明"仅限受邀私人使用"；默认关闭公开注册和匿名浏览 |
| 地图数据服务器设在境内的要求（《地图管理条例》第34条） | (b) | 高 | 同上。在大陆托管的实例只能是成员私用，不得对外公开（「未核实」：私用场景是否落入"互联网地图服务"） |
| 显示"问题地图"：OSM 标准瓦片在国界、藏南、阿克赛钦、南海等处的画法与《公开地图内容表示规范》第三、五、六条不一致 | (b)；(a) 影响较小 | 高（b）/ 低（a） | 设置 `minZoom≥10`，并用 `maxBounds` 限定在城市范围，不渲染全国或国际边界级别的视图；不自制或叠加任何边界图层 |
| 标注军事设施、要害部门等（《公开地图内容表示规范》第二十、二十一条；《地图管理条例》第37条） | 全部场景 | **高** | POI 分类写死为餐饮白名单（restaurant / fast_food / cafe / food stall 等）；不设自由类型；提供举报和管理员删除功能 |
| 外国人或外国组织在华"测绘"（《测绘法》第8、51条），以及使用高精度设备、批量轨迹采集 | (c) 向 OSM 贡献；(a) 成员在华采点 | 中 | 只记录"店名 + 粗略位置"，不采集也不上传 GPS 轨迹；不支持 RTK 或高精度模式；坐标保留 5 位小数（约 1 m）即可，界面上给出"约 10 m"的提示 |
| 从高德、百度、大众点评复制数据到 OSM（版权、ToS、OSM 社区规则） | (c) | **高**（对 OSM 项目） | 导入 OSM 的工具只接受成员实地确认的数据；源链接字段不得进入 OSM changeset |
| 坐标系混用（GCJ-02 / BD-09 当成 WGS-84） | 全部 | 中（数据质量） | 解析高德、百度链接时识别坐标系并换算；数据库只存 WGS-84，同时存 `coord_source` 字段 |
| ICP 备案 | (b) 大陆服务器 + 域名 | 中 | 大陆实例必须备案，否则 80/443 端口会被云厂商拦截；建议实例放在境外 |
| PIPL / 数据安全法 | (a)(b) | 低 | 数据最小化；不收集手机号或实名；地点数据只限餐饮 |
| GDPR（成员在欧盟） | (a) | 低至中 | 设计上满足"家庭豁免"的边界（邀请制、不公开、不商用）；同时提供导出、删除、最小数据，以防豁免不成立 |
| ODbL 共享相同方式（share-alike） | 全部 | 中 | 店铺位置图层按 ODbL 处理，或者与 OSM 餐饮数据严格分离；推荐文本另用 CC BY-SA 4.0；页面显示 OSM 署名 |
| OSMF 瓦片使用政策 | 全部 | 中 | 设置自定义 User-Agent，保留 Referer，不做离线预取；瓦片 URL 可配置 |
| X 账号展示导致去匿名化 | 全部 | 低至中 | X handle 设为可选；默认只在实例内部可见；不抓取 X 头像 |
| 德国 Impressum | (a) 德国成员托管 | 低 | 纯私人、家庭用途通常不需要；登录页不放广告和捐赠链接 |

场景定义：**(a)** 私人邀请制实例托管在境外（如德国），在中国境内访问；**(b)** 托管在中国大陆，且对公众开放；**(c)** 成员向 OpenStreetMap 贡献数据。

## 1. OSM 在中国的数据现状

### 1.1 全国完备度：coverage.osmchina.org

[coverage.osmchina.org](https://coverage.osmchina.org/) 是 OSM 中国社区做的乡镇级"OSM 要素完备度"可视化，统计截至 **2026 年 1 月**。评分总分 100 分，分四项：行政节点与边界 20、道路交通 30、**公共与商业设施 30**、建筑与土地利用 20。方法和结果见 OSM 日记系列《2025 年中国大陆乡镇 OSM 要素完备度分析报告》（[一](https://www.openstreetmap.org/user/Higashimado/diary/407990)、[二](https://www.openstreetmap.org/user/Higashimado/diary/408148)；2026-01-25 发布，2026-06-22 更新）。报告(二)中的实际数字如下：

- 全国全部样本的平均分只有 **44.67**。
- 省级平均分：上海 85.84、北京 77.72、天津 69.61、广东 58.28……**陕西 39.24，排倒数第二**（仅高于贵州 33.12）。
- 不到 2% 的乡镇接近满分。城市建成区以外的大多数乡镇在 24–36 分之间。
- 只有**不到 3%** 的乡镇中心标注了足够的公共与商业设施，**62%** 的乡镇中心没有标注任何公共或商业设施。
- 作者提醒，这个分数是特定规则下的量化指标，不代表对绘图质量的认可或否定。乡镇名单使用的是 2023 年统计局数据。

注意：这个指标只统计乡镇中心周边 1 km 和 3 km 范围，不能直接说明大城市核心区的餐饮覆盖情况，所以我们另外做了下面的实测。

### 1.2 Overpass 实测：西安回民街 vs 慕尼黑老城（2026-11-25）

我们用 `overpass-api.de` 各做了一次小查询（数据时间戳 2026-11-25T08:49Z），统计 `amenity=restaurant|fast_food|cafe` 的 node、way 和 relation。两个 bbox 面积都约为 1.11 km × 1.10 km：

- 西安：`34.257,108.932,34.267,108.944`，覆盖钟鼓楼和回民街一带
- 慕尼黑：`48.132,11.5676,48.142,11.5824`，以 Marienplatz 为中心

| 指标 | 西安 钟鼓楼/回民街 | 慕尼黑 老城 |
|---|---|---|
| 餐饮要素总数 | **112**（restaurant 59 / cafe 35 / fast_food 18） | **323**（restaurant 199 / cafe 88 / fast_food 36） |
| 有 `name` | 86（77%） | 321（99%） |
| 有 `opening_hours` | 14（12.5%） | 279（86%） |
| 有 `cuisine` | 45（40%） | 200（62%） |
| 最后编辑时间的中位数 | 2024-03-17 | 2025-11-15 |
| 最后编辑在 2020 年及以前 | 26 个（23%，其中 2016–2018 年 12 个） | 1 个 |
| 2026 年有过编辑 | 26 个 | 155 个 |
| 不同的最后编辑者 | 31 | 109 |

观察：

- **回民街的名店大多已经在 OSM 里**：老米家泡馍、贾三灌汤包子馆、定家小酥肉、刘纪孝腊牛羊肉店、盛志望、东南亚甑糕、樊记腊汁肉、老孙家等都有。但也能看到**重复或疑似重复**的条目，比如"盛志望麻酱酿皮铺 / 盛志望麻酱凉皮铺"、老孙家 3 条、老米家 2 条。另有 26 个条目没有名称。
- 西安同面积内的要素数量约为慕尼黑的 **1/3**，营业时间的覆盖率只有慕尼黑的约 1/7。考虑到回民街的实际摊位密度（数百家，「未核实」），OSM 漏掉的**街边小摊和小吃铺**估计占大多数，而 OSFM 种子数据正好是这一类。
- 有约 1/4 的条目 6 年以上没人更新，可能已经关店或搬迁。OSFM 的 UI 应该显示"OSM 最后更新时间"，并鼓励成员现场确认。
- bbox 里有不少连锁店（肯德基、星巴克、瑞幸），所以"本地小吃"的覆盖率比总数显示的更低。

### 1.3 质量问题

- **坐标偏移**：OSM wiki 的 [China](https://wiki.openstreetmap.org/wiki/China) 页面明确要求不要导入转换成 GCJ-02 的数据，也不要使用经过 GCJ-02 变换的影像。早年有人从国内地图复制数据，留下了 300–700 m 的系统偏移，目前偶尔还会遇到（实际规模「未核实」）。我们按 GCJ-02 公式算过，在回民街一带 WGS→GCJ 的偏移约 **462 m**，WGS→BD-09 约 **1.14 km**，相当于整条回民街的长度。所以只要混用一次坐标系，pin 就会落到另一个街区。
- **影像来源**：同一页面说明天地图影像**不能**用于描绘，只能作参考；新开发区域建议使用 Sentinel-2。
- **社区现状**：OSMChina 自称"OpenStreetMap 中国本地社区"，2021 年 10 月上线了官网 osmchina.org、地图和瓦片服务（见 [talk-cn 邮件](https://lists.openstreetmap.org/pipermail/talk-cn/2021-October/000151.html)、[GitHub](https://github.com/OSMChina)）。社区交流主要在 Telegram 和 Discord 上。社区维护的 [China tagging guidelines](https://wiki.openstreetmap.org/wiki/China_tagging_guidelines) 说得很直接："It is simply illegal to map in China"，同时警告："DO NOT USE ANY HIGH-ACCURACY SURVEYING EQUIPMENT IN CHINA!" 和 "DO NOT MAP MILITARY…"。osmchina.org 本身在调研时返回 403，没有核实它目前的运营状态。
- **可访问性**：从大陆访问 openstreetmap.org 和 tile.openstreetmap.org 时，速度和可用性不稳定（「未核实」，没有在大陆实测）。建议实例支持配置备用瓦片源，或者自建瓦片。

## 2. 坐标系：WGS-84 / GCJ-02 / BD-09

| 坐标系 | 使用方 | 说明 |
|---|---|---|
| WGS-84 | GPS 原始输出、OSM、Google 海外、iOS CoreLocation | 国际标准 |
| GCJ-02（"火星坐标"） | 高德、腾讯、Apple 地图中国区、Google 中国区底图 | 对 WGS-84 做非线性加偏，偏移约 100–700 m |
| BD-09 | 百度 | 在 GCJ-02 基础上再加一次偏移 |

**法律依据**：一般认为出处是强制性国标 GB 20263-2006《导航电子地图安全处理技术基本要求》，该标准要求导航电子地图在出版、销售、传播、展示前做"空间位置技术处理"（[Wikipedia: Restrictions on geographic data in China](https://en.wikipedia.org/wiki/Restrictions_on_geographic_data_in_China)，第 4.1 条的原文「未核实」，标准文本不公开发售或需付费）。上位法依据是《公开地图内容表示规范》第十七条："利用涉及国家秘密的测绘成果编制地图的，应当依法使用经有关主管部门认定的保密处理技术进行处理"。2024 年的 GB/T 44489 仍然引用 GB 20263。

**OSFM 需要转换吗？**

- **底图是 OSM 瓦片、pin 来自浏览器定位或手动点选**：**不需要转换**，两边都是 WGS-84。
- **浏览器 Geolocation 和 iOS 定位**：返回 WGS-84（Apple 文档写的是 WGS 84 参考系，见 [Apple Developer Forums](https://developer.apple.com/forums/thread/797697)）。国产 Android ROM 的系统级 `LocationManager` 返回的 GPS fix 通常也是 WGS-84；但如果 App 通过高德、百度 SDK 或微信接口定位，常常是 GCJ-02 或 BD-09。浏览器在大陆用 Wi-Fi 或网络定位时，结果的来源和坐标系都可能不确定（「未核实」，建议在大陆真机上做 A/B 测试）。
- **需要转换的情况**：
  1. 成员粘贴的高德、腾讯、大众点评、美团链接或坐标，按 GCJ-02 处理（点评和美团用的坐标系「未核实」，大概率是 GCJ-02）；
  2. 百度链接按 BD-09 处理；
  3. 叠加国内厂商的瓦片或影像（高德、天地图等），需要把 WGS-84 的 pin 转成 GCJ-02 来显示，或者反过来。
- **实现建议**：数据库只存 WGS-84，另加字段 `coord_source ∈ {gps, manual_osm, amap, baidu, unknown}` 和 `precision_m`。GCJ→WGS 只有近似反算，迭代后误差可以小于 1 m，推荐 [PRCoords](https://github.com/Artoria2e5/PRCoords)（公共领域许可）或 [gcoord](https://github.com/hujiulong/gcoord)。
- **法律提示**：网上流传"公开纠偏算法或纠偏数据违法"的说法，我们没有找到明确的法条依据（「未核实」）。为了保守起见，只对单个用户输入的餐馆坐标做换算，不提供批量"纠偏"国内地图数据的功能，也不把换算后的高德、百度坐标上传到 OSM（无论如何这都违反 OSM 的来源规则，见 §4.3）。

## 3. 中国法律环境

### 3.1 关键法条

**《测绘法》（2017 年修订）**

- 第2条：测绘的定义，包括对自然地理要素或地表人工设施的形状、大小、空间位置及其属性进行测定、采集、表述。按字面理解，"采集餐馆位置"也可能落入这个定义。
- 第8条：外国的组织或者个人在华从事测绘活动，须经国务院测绘地理信息主管部门会同军队测绘部门批准；还应当与中方有关部门或单位合作，并不得涉及国家秘密和危害国家安全（第二款据通行版本，未逐字核对）。
- 第27条：从事测绘活动的单位应当取得相应等级的测绘资质证书。
- 第38条：互联网地图服务提供者应当使用经依法审核批准的地图，并加强对新增内容的核校。
- 第51条：外国组织或个人擅自测绘的，没收测绘成果和工具，处 10万–50万元罚款；情节严重的，处 50万–100万元罚款，并可限期出境或驱逐出境。
- 第55条：未取得资质擅自测绘的处罚。
- 第62条：地图或互联网地图服务不符合规定的处罚。
- 来源：[维基文库](https://zh.wikisource.org/wiki/中华人民共和国测绘法_(2017年))。另据[自然资源部 2026 年 8 月发布会](https://www.sohu.com/a/1068845187_121106822)，《测绘法》已在推动修订，但没有见到草案。2026 年 7 月出台了《自然资源部非涉密测绘地理信息成果管理办法》（[自然资办发〔2026〕14号](http://www.hunan.gov.cn/zqt/zcsd/202608/t20260818_34046346.html)），规范对象是成果保管单位，与 OSFM 关系不大。

**《地图管理条例》（2015，国务院令第664号）**（[维基文库](https://zh.wikisource.org/wiki/地图管理条例)）

- 第2条：适用于境内"向社会公开的地图"的编制、审核、出版和互联网地图服务。
- 第8条：地图上不得表示危害国家统一、主权和领土完整的内容，或者属于国家秘密的内容。
- 第15条：国家实行地图审核制度，向社会公开的地图应当送审；**景区图、街区图、地铁线路图等内容简单的地图除外**。
- 第33条：从事**地理位置定位、地理信息上传标注、地图数据库开发**等互联网地图服务的，应当取得相应的测绘资质。
- 第34条：存放地图数据的服务器应当设在境内。
- 第35条：收集用户信息应当明示目的，并经用户同意。
- 第36、37条：不得存储或上传标注"不得表示"的内容。
- 第38条：使用审核批准的地图，核查新增内容。
- 第54条：使用未经审核的地图，或者不核查新增内容的，处最高 20 万元罚款。
- 第55条：上传标注违规内容的，处最高 10 万元罚款。
- 审图号要标在页面左下角，互联网地图的审图号有效期两年（据《地图审核管理规定》，[外交部汇编 PDF](https://www.mfa.gov.cn/wjb_673085/zzjg_673183/bjhysws_674671/bhflfg/dtdmxgfl/202303/P020230313586143347764.pdf)）。

**测绘资质**：按 2021 年《测绘资质分类分级标准》，"互联网地图服务"是一个专业类别，分甲、乙两级，业务范围是地理位置定位、地理信息上传标注、地图数据库开发（[广东省资质目录](https://nr.gd.gov.cn/attachment/0/505/505211/4035063.doc)）。个人**无法**申请资质。外资申请受《外国的组织或者个人来华测绘管理暂行办法》限制。

**《公开地图内容表示规范》（自然资规〔2023〕2号，有效期 5 年，大约到 2028 年 2 月）**（[gov.cn 原文附件](https://www.gov.cn/zhengce/zhengceku/2023-02/17/content_5741977.htm)，已下载并核对原文）

- 第三、五、六、七、八条：国界、南海断续线、钓鱼岛、台湾等的画法。第十二条：克什米尔的画法。
- **第十八条**："我国境内公开悬挂标牌的单位可在地图上表示单位名称。用于公共服务的设施，可在地图上表示其名称等可公开属性信息。" 所以**餐馆名称和位置本身属于可以公开表示的内容**，这是 OSFM 最重要的合规依据。
- **第十九条**：地图平面精度"应当不优于 10 米（不含）"。手机 GPS 精度一般在 3–10 m，严格来说，公开地图上的点位精度不应优于 10 m。这一条对境外私人实例的约束力不明（「未核实」）；在大陆公开托管时需要考虑。
- **第二十条**：不得表示军事设施、危险品存放地、核电站、国家安全等要害部门、油气管线、军民合用机场港口的重要设施、**卫星导航定位基准站**等。
- **第二十一条**：不得表示监狱、看守所的属性（名称除外），以及重要桥梁的限高限重、江河水深、电力通信管线等属性。
- 第二十二条：遥感影像分辨率不得优于 0.5 m。

**其他相关法规**

- **ICP 备案**：《互联网信息服务管理办法》第4条规定，非经营性互联网信息服务实行备案制度。大陆服务器加域名提供网站服务必须备案，否则云厂商会拦截 80/443 端口。如果有评论、发帖功能，还会涉及《互联网跟帖评论服务管理规定》，以及《网络安全法》第24条的实名要求（条文未逐字核对）。
- **《数据安全法》**：第2条规定，在境外处理数据、损害中国国家安全或公共利益的，也要追究责任。餐馆 POI 属于公开的商业信息，一般不属于"重要数据"。但如果大批量、高精度地采集敏感区域周边的地理数据，就可能被认定为重要数据（「未核实」具体目录）。
- **《个人信息保护法》**：第3条规定，向境内自然人提供服务的境外处理活动也适用本法；第72条规定，**自然人因个人或者家庭事务处理个人信息的，不适用本法**（条文据记忆，见[维基文库全文](https://zh.wikisource.org/wiki/中华人民共和国个人信息保护法)，未逐字核对）。小圈子实例的管理员很可能属于这种情况，但公开实例不属于。
- **执法动向**：国家安全机关在 2025-09 通报了境外人员携带测绘仪潜入军事管理区周边测绘的案件（[新华网](https://www.news.cn/politics/20250909/3e53ef37afd04f5a9667441f2fabf151/c.html)），2026-01 又发布了"警惕以学术交流为掩护开展非法测绘"的提示（[新华网](https://www.news.cn/politics/20260113/5fe35636f177440eb90777c23e71e0c8/c.html)）。公开案例都涉及军事或敏感区域、专业设备或数据出境，**没有看到因标注餐馆被处罚的公开案例**（「未核实」是否完全不存在）。另外，2026-07-01 施行的《民族团结进步促进法》被 OSM 社区讨论过对贡献者的影响（[论坛帖](https://community.openstreetmap.org/t/discussion-possible-implications-of-chinas-new-ethnic-unity-and-progress-law-for-osm-contributors/145989)）。回民街属于少数民族聚居街区，内容描述（推荐语、标签）要避免涉及民族、宗教的负面或歧视性表述。

### 3.2 三种场景的风险评估

**(a) 境外托管的私人邀请制实例，从中国访问**：**低至中**

- 不是"向社会公开的地图"（条例第2条），也不在境内提供服务，所以审图号、资质、服务器在境内这些条款很难直接适用。
- 剩下的风险是：(1) 成员在华的"采集"行为，按《测绘法》第2条字面上可能算测绘；外籍成员还要考虑第8条。但餐馆位置属于第十八条允许公开表示的内容，用的也是普通手机，实际风险很低。(2) 数据出境：成员把位置写入境外服务器。只要内容限于餐饮 POI，风险低。
- 对策：严格的餐饮白名单、不收集 GPS 轨迹、不提供高精度模式。

**(b) 在中国大陆托管且对公众开放**：**高**，项目不应支持

- 带用户上传标注的地图服务需要测绘资质（个人拿不到）和审图号（OSM 底图过不了审：国界画法不同、没有加偏、精度过高）。另外还要 ICP 备案、跟帖评论管理和实名。
- 如果大陆成员坚持在境内自托管，只能做成**不对外开放的私用实例**：内网或 VPN 访问、不做公开 ICP 网站、`minZoom` 限定在城市级。即便如此，是否落入"互联网地图服务"也说不清（「未核实」），README 里要写明风险由部署者自担。

**(c) 向 OSM 贡献**：**中**

- OSM wiki 自己的说法是：未经授权的私人测绘在大陆是违法的，"This seems to outlaw the entire OSM project and any participation or contribution"。执法重点在新疆、西藏和敏感设施附近（[wiki: China](https://wiki.openstreetmap.org/wiki/China)）。
- 只添加带公开招牌的餐馆节点，在法理上有第十八条支撑，风险相对低。但下面这些仍要注意：
  - 外籍成员在华实地采点；
  - 上传 GPS 轨迹（OSM 的 GPS traces 是公开的）；
  - 在敏感区域附近编辑；
  - 实名账号与线下身份关联（社区的建议是保持匿名）。
- 建议：用匿名 OSM 账号；不上传轨迹；只改 `amenity=*` 餐饮节点和 `name`、`cuisine`、`opening_hours` 这类公开属性；不碰边界、地名争议和军事相关对象。

### 3.3 产品红线（必须写进设计文档和贡献指南）

1. **POI 类型白名单**：只允许餐饮类。禁止自定义类型，禁止标注或描述军事设施、要害部门、监狱看守所、油气管线、基准站、桥梁限高限重等（对应规范第二十、二十一条）。
2. **不画任何边界**：不提供行政区或国界图层，不提供"全国视图"；默认 `minZoom≥10`，`maxBounds` 只包含实例关心的城市。
3. **不生成、不展示、不存储 GPS 轨迹**，不做"实时位置共享"。坐标精度限制在 5 位小数。
4. **不内置高德、百度、腾讯的 SDK 或瓦片作为默认底图**（避免 ToS 冲突和坐标混用）。如果作为可选底图，需要明确标注坐标系，并只在客户端做显示变换。
5. **不提供批量纠偏或导出国内地图数据的功能**。
6. **不支持在中国大陆公开部署**（README 和部署文档里写清楚）。
7. **内容治理**：推荐语不得涉及民族、宗教歧视或政治内容，管理员要能删除。
8. **不使用遥感影像图层**（规范第二十二条；也避免和 OSM 的影像授权冲突）。

## 4. OSM 许可（ODbL 1.0）

### 4.1 显示 OSM 瓦片：署名

- 栅格瓦片属于 **Produced Work**（[Produced Work Guideline](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Produced_Work_-_Guideline)，2014-06-06 批准）。只要"公开使用"，就要附 ODbL 4.3 规定的署名，可以用任意许可发布。
- 署名要求：在右下角标注 "© OpenStreetMap contributors" 并链接 openstreetmap.org/copyright；不得被 UI 遮挡，也不得藏在开关后面（见[瓦片政策](https://operations.osmfoundation.org/policies/tiles/)和 [Attribution Guideline](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines)）。
- 注意：ODbL 对 **"Publicly"** 的定义是"向 You 本人或受 You 控制者以外的人"（[ODbL 1.0 §1](https://opendatacommons.org/licenses/odbl/1-0/)）。所以**邀请制小圈子也算公开使用**，署名和共享相同方式的义务都适用，不能用"私密"来规避。

### 4.2 我们的数据库：Collective 还是 Derivative？

- **[Collective Database Guideline](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Collective_Database_Guideline_Guideline)**（2016-06-17 批准）：同一 regional cut 内，某一数据类型如果"全部来自 OSM，或者全部不来自 OSM"，两个数据集就算独立，组合成的是 Collective Database，share-alike 只约束 OSM 部分。允许通过数据库 key（例如 OSM node ID）做引用和 join。
  - 指南里的例子：**"你为餐馆提供电话号码，并通过引用关联到 OSM 名称"，电话号码不受 share-alike 约束**。
  - 反例：把**私有餐馆清单与 OSM 合并**，就落在指南保护范围之外，可能整体需要按 ODbL 共享。
- **[Horizontal Map Layers Guideline](https://osmfoundation.org/wiki/Community_Guidelines/Horizontal_Map_Layers_-_Guideline)**（2014-06-06）：按 Feature Type 判断。"用 OSM 做底图，尽合理努力排除所有餐馆，再加上自己的餐馆图层"可以不共享；"对照 OSM 图层在某个区域补充餐馆"，或者"补充 OSM 里没有的某类对象"，则**需要**共享。
- **[Substantial Guideline](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Substantial_-_Guideline)**：一次性提取少于 100 个要素算非实质性；按自己主观标准挑选（比如"我去过的店"）也可以。但"系统性提取某区域所有餐馆"不算非实质性，而且多次小量提取会合并计算。

**对 OSFM 的含义**：

- **推荐记录**（推荐人、时间段、来源链接、评语）相当于"电话号码"例子里的电话号码：通过 `osm_type/osm_id` 引用 OSM 节点、**不复制 OSM 的坐标和名称**时，属于 Collective，推荐数据**不受** share-alike 约束。
- **店铺 pin 图层**：成员自己添加、OSM 里没有的回民街小摊，本质上是"对照 OSM 补充餐馆"，按 Horizontal Layers 指南很可能会触发 share-alike。如果从 OSM 复制了名称和坐标来建 pin，那就是直接提取。
- **推荐方案**：**把"店铺位置"图层（名称、坐标、OSM 引用）整体声明为 ODbL 1.0**，实例在导出页提供这一图层的 ODbL 下载（满足 4.6）。这样合规成本最低，也和"把新店贡献回 OSM"的目标一致。推荐、评语图层单独存放，单独授权。

### 4.3 把我们的数据导入 OSM

- [Contributor Terms](https://osmfoundation.org/wiki/Licence/Contributor_Terms)：贡献者保留版权，同时授予 OSMF 广泛许可，并保证数据来源与 ODbL 兼容。
- [Legal FAQ](https://wiki.openstreetmap.org/wiki/Legal_FAQ)："Most maps cannot be used as the base of any data uploaded to OSM"。Google 地图、街景、商业地图都不能作为来源，高德、百度、大众点评、美团同样不行：这里涉及 ToS 合同约束、著作权，以及欧盟的数据库权（sui generis）。天地图也不能用于描绘（[wiki: China](https://wiki.openstreetmap.org/wiki/China)）。
- 因此，OSFM 的"贡献到 OSM"功能只能导出**成员实地确认**的数据（店名来自招牌，位置来自现场 GPS 或对照合规影像）。**来源链接字段（点评、高德、X 帖子）绝不能进入 changeset**；从高德或百度换算来的坐标也不能上传。还应遵守 [Automated Edits / Import 规范](https://wiki.openstreetmap.org/wiki/Import/Guidelines)：小批量手动提交，不做批量导入。

### 4.4 用户贡献内容（推荐语）的许可

- 建议：推荐语和评语默认采用 **CC BY-SA 4.0**，在注册页让用户勾选同意。如果实例希望更封闭，也可以**由贡献者保留版权，并授予实例"展示、导出、迁移"的非独占许可**。
- 两种做法都要支持用户导出和删除自己的内容。删除后，已经按 CC 授权传出去的副本无法收回，这一点要在 UI 里提示。
- 软件本身的许可（如 AGPL 或 MIT）与数据许可分开声明。

## 5. 欧盟 / 德国

- **GDPR 家庭豁免**：GDPR 第2(2)(c)条规定，纯个人或家庭活动不适用 GDPR。Recital 18 提到社交和线上活动也可能属于这种情况，但**为个人或家庭活动提供处理手段的控制者或处理者仍受 GDPR 约束**。CJEU 的 *Lindqvist*（C‑101/01）认定，向不特定人群公开发布不适用豁免（[摘要](https://www.thomashelbing.com/en/wissen/dsgvo-hub/rechtsprechung/1.4.43-eugh-lindqvist)）；*Ryneš*（C‑212/13）认定豁免要从严解释（[摘要](https://www.thomashelbing.com/en/wissen/dsgvo-hub/rechtsprechung/1.4.20-eugh-rynes)）。爱尔兰 DPC 的说法是：只要不与职业或商业活动相关、**也不公开**，就可以适用豁免（[DPC FAQ](https://dataprotection.ie/en/faqs/general/what-household-exemption)）。
  - **结论**：一个人在自家硬件上，为一个熟人群聊运行邀请制、非商业、不对外公开的实例，**很可能**落入家庭豁免。但群越大、成员之间越陌生、越有公开页面或商业因素，豁免就越不可靠。例如几百人的群、公开可访问的 pin 页面、广告或捐赠，都会削弱豁免。另外，**提供托管服务的第三方**（例如替别人托管实例的人）不能享受豁免。
  - **软件层面的建议**（即使豁免成立也应该做，属于 privacy by design）：
    1. 一键导出个人数据（JSON，以及 ODbL 图层的 GeoJSON）；
    2. 删除账号时，推荐要么匿名化（显示"已退出成员"），要么一起删除，由用户选择；
    3. 最小化数据：只保存昵称和可选的 X handle，不收集邮箱以外的身份信息，不做访问日志分析或第三方统计，不加载 Google Fonts 和 CDN 追踪器；
    4. 不收集位置轨迹，pin 的创建时间可以选择模糊化；
    5. 提供隐私说明模板，以及"实例管理员职责"文档。
- **Cookie（德国 TDDDG §25）**：只用严格必要的会话 cookie 时不需要 cookie banner。
- **Impressum（德国 DDG §5，2024-05-14 起取代 TMG）**：只适用于"geschäftsmäßige, in der Regel gegen Entgelt angebotene"数字服务。只服务于个人、家庭目的的私人站点原则上不需要（见 [e-recht24](https://e-recht24.de/artikel/datenschutz/209.html)、[IHK München](https://www.ihk-muenchen.de/ratgeber/recht/internetrecht/impressum/)）。"geschäftsmäßig"的范围解释得很宽，放广告、收捐赠都可能触发。建议：登录页不放捐赠或广告链接，部署文档里提示德国部署者自行判断。另外，《媒体国家条约》MStV §18 对"不完全服务于个人或家庭目的"的站点要求提供姓名和地址（条文未逐字核对）。

## 6. 展示 X（Twitter）账号

- **ToS**：OSFM 只保存并显示用户**自愿填写**的 handle 字符串，并链接到 `x.com/<handle>`，这不属于 X API 的使用，也不受开发者协议约束。如果要抓取 X 的头像或帖子内容，就会违反 [X 服务条款](https://x.com/en/tos)对未经同意爬取的禁止条款（条款原文未逐字核对）。嵌入单条帖子请用官方 oEmbed。另外，X 在中国大陆无法直接访问，链接对大陆成员来说是"死链"。
- **去匿名化风险**：把 X 化名、OSFM 里的真实行程（时间段加地点）以及推荐人签名关联在一起后，可以推断出出行时间、常去地点，甚至住处附近。如果有人把实例数据泄露或截图外传，化名身份就可能被识破。
  - 对策：X handle 设为可选，并只在实例内部可见；不在公开导出（ODbL 图层）里包含推荐人和 handle；"时间段"建议粗化到"午市 / 晚市 / 夜宵"，不精确到日期；可以提供"匿名推荐"选项。

## 7. 瓦片使用政策（OSMF）

依据 [Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)：

- 使用 `https://tile.openstreetmap.org/{z}/{x}/{y}.png`（不得用 HTTP；其他子域名可能被撤销）。
- 设置**独特且稳定的 User-Agent**（包含应用名和联系方式），不要用库自带的默认 UA。网页端要保留有效的 Referer，不要设置会去掉 Referer 的 Referrer-Policy。
- 遵守缓存头（Cache-Control、ETag）。无法读取缓存头时，至少缓存 7 天。不要发送 `no-cache`。
- **禁止**预取、批量下载、"离线保存区域"。不推荐自建缓存代理；如果非要用，代理必须遵守上述头部规则，并带可联系的 UA。
- 服务尽力而为，可能不经通知被封禁。
- 建议：瓦片 URL 做成可配置项；文档里推荐重度使用的实例改用自建瓦片或商业瓦片（MapTiler、Stadia 等，需遵守它们各自的条款）。如果需要离线浏览（比如在大陆网络不稳定时），只能用自建或允许离线的瓦片源，例如 Protomaps 的 PMTiles 单文件。
- 可以加一个"报告地图问题"链接，指向 https://www.openstreetmap.org/fixthemap 。
